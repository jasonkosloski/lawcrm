# Settings and Firm Admin

The `/settings` area, grouped in the side nav as You (Profile, Security, Notifications), Firm (Firm info, Team, Roles), Practice (Practice areas, Document templates, Records request types) and Admin (Integrations, Activity log). Automations lives at `/settings/automations` but is reached from the main sidebar. Billing and rates is an unlinked placeholder until it ships: only pages that do something are in the nav. Auth internals are in [auth.md](auth.md).
Related: [PERMISSIONS.md](../PERMISSIONS.md), [deadlines-and-tasks.md](deadlines-and-tasks.md) (Automations), [documents.md](documents.md) (templates)

## Shipped

- [x] **Route framework** — `/settings` layout with left-rail section nav; entries the user cannot see are hidden. Routes are gated end-to-end on permission keys: `/settings/practice-areas` (+ `[id]`) on `firm.manage_practice_areas`; `/settings/billing` on `firm.edit_info`; `/settings/activity` on `firm.view_activity`; `/settings/integrations` and `/settings/security` are self-service (identity-scoped, no key).
- [x] **Profile** — self-edit form (name, initials, phone, bar number, avatar URL, time zone, default event visibility). Right rail shows identity + governance read-only (email, role, admin badge, active status, member-since, firm) with a chip to /settings/team. Bar numbers are a "Bar admissions" list (state + number), not one field ([ADR-069](../decisions/069-lead-attorneys-hold-a-bar-admission.md)); the same editor is in Team → Edit member and Invite.
- [x] **Team** — firm-scoped roster (admins first, then active alphabetically). Admins get a per-row menu (Edit / Sign out everywhere / Reset sign-in link / Resend invite) and an "Invite member" composer. Admin and privileged-role controls are locked for non-Admin holders of `firm.manage_team_directory`. Invariants: at least one Admin; cannot deactivate yourself; unique email on invite. Invite emails a Clerk invitation (Google sign-in); deactivate/reactivate bans/unbans in Clerk after the DB commit (a Clerk failure is a warning; the DB already denies access). Wrapper: `src/lib/clerk-admin.ts`. See [auth.md](auth.md).
- [x] **Activity log** — cross-matter audit page `/settings/activity` reading `ActivityLog`: URL-driven filter pills (Communications = email + call, Documents, Evidence, Security; invoice/expense/permission writers still log as "filing"), user dropdown, from/to dates. Gated on `firm.view_activity`. 200-row cap.
- [x] **Roles** — first-class permission roles (`Admin` short-circuits everything; `default` is auto-assigned). Custom roles get whatever the matrix grants. The **permissions matrix** (for `firm.manage_permissions`) has every permission key (grouped by category) on the Y-axis, every role on X, checkbox at the intersection; the Admin column is checked and locked. Runtime checks in `src/lib/permission-check.ts`; reference in [PERMISSIONS.md](../PERMISSIONS.md).
- [x] **Firm info** — first-class `Firm` model (name, short name, EIN, website, phone, email, address, country, established date, logo URL). Holders of `firm.edit_info` get an inline edit form (audit entry names only the changed fields); others read-only. Right rail: team count + admin list.
- [x] **Practice area + stage editing** — `/settings/practice-areas/[id]` has full stage CRUD: create, rename, mark/unmark terminal, reorder up/down, archive (refused while active matters sit in the stage). Gated on `firm.manage_practice_areas`. Practice-area / stage / calendar-default mutations write `settings` audit rows (excluded from the dashboard feed). Turning SOL tracking off only stops auto-computing: existing SOL dates and SOL deadlines are kept. Create/edit forms keep user input after a server validation error. Recoloring an area recolors matters still on the old color (see [platform-quality.md](platform-quality.md)).
- [x] **Security page** (identity-scoped, no key) — `/settings/security`: signed-in devices (live from Clerk via `listActiveStaffSessions`: browser, device, location, last active in the user's zone, "This device" badge, per-device Revoke through `revokeMySession`) and the user's own sign-in history. No password UI: sign-in is Google via Clerk.
  - Auth audit: sign-ins and sign-outs (from the signed Clerk webhook), admin invite / member update / sign-out-everywhere / sign-in link reset / ban sync all land in `ActivityLog` as `type: "auth"` with IP + user agent (`src/lib/auth-events.ts`); filterable under "Security" on /settings/activity, excluded from the dashboard feed.
  - Session revocation is Clerk's: per-device revoke and admin sign-out-everywhere / ban call the Clerk Backend API. Pre-Clerk rows (failed sign-in, password change, unlock) keep their stored titles on /settings/activity but no longer appear in the per-user history here, which filters on the current `AUTH_EVENT_TITLES`.
  - Team sign-in management (`firm.manage_team_directory`, Admin-class targets Admin-only): Sign out everywhere revokes all Clerk sessions; Reset sign-in link revokes the old identity's sessions first and only then clears `clerkUserId` (so a surviving session can't re-link), the member re-links on their next verified-email sign-in; Resend invite is offered until the first sign-in.
- [x] **Integrations page** — Gmail per-user connect / reconnect / disconnect card (address, sync-status chip, last sync, thread count, `syncError` surfaced, multi-account list), callback banners, "not configured" env guidance. Google Calendar rides the same card (per-account "Calendar sync on" vs "Reconnect to enable calendar sync"). Self-service (connecting YOUR mailbox is identity-scoped like notifications). `CRON_SECRET` is required in production, and the Google Cloud project needs BOTH the Gmail and Calendar APIs enabled. See [communication-email.md](communication-email.md), [google-calendar-sync.md](google-calendar-sync.md).

- [x] **Originating-document switch and label** (2026-10-20, ADR-056) — Firm info has "Require a signed originating document to open a matter" (`Firm.requireOriginatingDoc`, Admin only, default off). Each practice area's form has an "Originating document" label (blank = "Fee agreement"), gated on `firm.manage_practice_areas`.
- [x] **Court formats** (2026-10-22, ADR-065) — `/settings/court-formats` lists, adds, edits, archives/restores and deletes firm court formats (name, court system, formatting overrides, paper size, block replacements); gated on `court_formats.add/edit/delete`, and the page and nav entry are hidden from staff holding none. Venues gain a court format and a caption name, set on the venue form under the existing `venues.*` keys.
- [x] **Venues and matter intake settings** (2026-10-20, ADR-055) — `/settings/venues` manages the firm's court/venue list (name, one address — two street lines, city, state, ZIP — and county; add, edit, archive/restore, delete); state is required free text defaulting to the firm's state. Gated on the `venues.*` keys; the migration gave `venues.add` to every role that already had `matters.create`. Changes log as firm-level `settings` rows. The firm's matter-name template is on Firm info; each practice area's form adds a name-template override and the required-field checklist for new matters.

# Intake (leads)

Lead queue, new-intake form, lead detail with Overview / Time / Notes / Tasks / Events / Documents / Records / Communication tabs, conflict checks, decline, restricted intake and lead-to-matter conversion are shipped. Everything created on a lead carries forward to the matter on conversion.
Related: [ADR-049](../decisions/049-restricted-intake-is-an-opt-in-wall-carried-to-the-matter.md), [ADR-044](../decisions/044-intake-notes-share-the-note-table-scoped.md), [ADR-045](../decisions/045-intake-tasks-and-events-reuse-task-and.md), [ADR-046](../decisions/046-intake-documents-share-document-and-documentfolder-scoped.md), [ADR-019](../decisions/019-deadline-rules-task-lists-as-firm-libraries.md), [ADR-026](../decisions/026-conflict-matcher-scope-own-contact-exclusion-inactive.md), [records-requests.md](records-requests.md)

## Shipped

- [x] **Restricted intake (lead ethical walls)** (2026-10-19, ADR-049) — opt-in `Lead.restricted` with a `LeadTeamMember` team. A restricted lead and everything on it (tabs, downloads, uploads, by-id actions, search, Cmd+K, queue + counts, dashboard tasks/agenda, calendar as Busy, activity feeds) is visible only to its team, `intake.view_restricted` holders and Admins; everyone else gets 404. Lead Overview "Access" card (`intake.restrict`): Restrict / Open to firm (actor auto-added), add/remove members with a matter-team role, last member can't be removed; lock badge in the header and queue. Conversion copies the flag to `Matter.restricted` and the team to the matter team (converter stays lead). Open leads behave exactly as before.
- [x] **Conversion originating-document gate** (2026-10-20, ADR-056) — with the firm switch on, `convertLeadToMatter` requires a signed originating document (one of the lead's existing documents; the dialog has no new upload); off, nothing changes.
- [x] **Intake queue — v1 list** — sortable table; active leads first: unscored (fresh) leads newest-first, then scored by score desc (`sortIntakeQueue`). Lists every open lead (a notice appears past the 1,000-lead safety bound); closed history pages behind them (`?page=N`, 200 per page); statute column is a live countdown; Decline / Convert buttons depend on role.
- [x] **New intake form (`/intake/new`)** (2026-10-17) — `createLead` gated by `intake.create` (queue "New intake" button and the Cmd+K row). Person: type-ahead over active, unmerged contacts links a repeat caller; else a typed email matching an active contact (case-insensitive) links to it (form says so before save); else a new `client` contact (+ primary ContactPhone). Inquiry: source + detail, summary, incident date (date-only, ADR-012), location, injuries, prior counsel. Conflict matcher runs on save and the result is stored; activity-logged; lands on the lead page.
- [x] **Lead detail — v1 page and tabs** — case summary, assessment bars (liability + damages), contact card, intake meta, conflict-check card, converted-matter link. Communication tab shows email threads filed to the lead (`EmailThread.leadId`, see [email](communication-email.md); no contact-address matching) plus the contact's SMS/call/voicemail, and has a Compose button.
- [x] **Lead -> Contact integration** — every lead hangs off a first-class Contact via `Lead.contactId`; conversion reuses it.
- [x] **Conversion conflict gate** (2026-10-18) — `convertLeadToMatter` re-runs the matcher at submit: a live conflict refuses (only a recorded override gets through), possible conflicts need a review tick in the dialog, and the outcome is on the matter timeline. [ADR-050](../decisions/050-lead-conversion-re-runs-the-conflict-check.md).
- [x] **Conflict check automation (v1)** — pure matcher `src/lib/conflict-check.ts`. Email match: conflict if the contact appears as opposing-side, else warn. Severity clear/warn/conflict. `runLeadConflictCheck` persists status + timestamp; `overrideLeadConflictCheck` flips warn/conflict to "override" with a 5+ char justification. Keys `intake.conflict_check.run/override`; audit-logged. The lead's own Contact never matches itself; deactivated contacts still parties on active matters stay in the hard (opposing) tier; merged-away contacts are excluded. Audit titles name the lead.
- [x] **Decline lead** — topbar action with optional internal reason; `Lead.stage` = "declined", leaves the active queue. Conditional (`stage notIn converted, declined`): a second decline changes nothing and writes no second audit row.
- [x] **Convert lead to matter — v1 + integrity (W8b)** — topbar action with practice area, initial stage, matter name, billing type (from the practice area's allowed list). One transaction creates the Matter (reusing the lead's Contact), MatterTeamMember, UserMatterPin and the client `MatterContact` row (so the Parties tab shows the client); clears stale `declineReason`; lead summary/location/incident date/injuries/source flow into Matter.description. The lead is claimed with a conditional `updateMany` (id + stage read): a double submit or stale tab matches 0 rows, rolls back and shows a clear form error. Deploy step: run the client party-row backfill once per environment (`docs/DEPLOY_BACKFILLS.md`).

## Notes

- Scope pattern: lead-scoped records use "exactly one of (matterId, leadId)" (tasks/events: at most one) and a `RecordScope`; revalidation via `scopePaths(scope, ...)`. All lead tabs refuse writes on converted leads and carry their records forward in `convertLeadToMatter`.
- Template generation on a lead: `resolveMergeContext` accepts a lead; `client.*` comes from the lead's contact, `matter.*` fields resolve to null and render as the engine's visible "[… — not on file]" placeholder (reported missing); `firm.*`, `user.*`, `today` unchanged.
- On lead documents, matter-only links (evidence links on flags) are hidden. Every reader of `Document.matterId` / `DocumentFolder.matterId` must tolerate null (search, `CHILD_RESOLVERS` in `matter-access.ts`, email-attachment and copy paths, flagged-moment queries).
- Email attachments, "Copy to…", flags and delete reference-counting work unchanged on lead documents; copy targets must be in the same scope.
- `matter-access-guards.test.ts` allowlist entries only where an action genuinely has no matter.
- Lead wall: every new lead page calls `assertLeadAccess` after `requireUser` (static test); every action that touches a `leadId` calls a lead-aware helper (`assertLeadAccess`, `assertScopeAccess`, `assertChildMatterAccess`, `assertRecordAccess`); lists of lead-bearing models use `optionalRecordAccessClause`; lead-scoped `logActivity` calls pass `leadId`.

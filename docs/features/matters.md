# Matters

Matters list (table/kanban), matter detail shell and the Overview, Parties, Deadlines, Tasks, Notes, Timeline and Events tabs, team management, stage handling and statute-of-limitations tracking are shipped. The `/matters/new` form works; v2 follow-ups are listed below.
Documents, Billing, Communication, settlements and expenses are in their own feature files.
Related: [ADR-006](../decisions/006-matter-urls-use-cuid-not-slug.md), [ADR-010](../decisions/010-per-user-matter-pins-usermatterpin-join-table.md), [ADR-021](../decisions/021-matter-tabs-honour-calendar-visibility-and-money.md), [ADR-025](../decisions/025-captures-do-not-inherit-the-primary-s.md), [ADR-027](../decisions/027-the-matter-owns-the-statute-of-limitations.md), [ADR-035](../decisions/035-statute-periods-are-calendar-amount-unit-computed.md), [ADR-039](../decisions/039-matter-team-access-ethical-walls.md), [ADR-054](../decisions/054-new-matter-screens-both-directions-and-overrides-on-the-matter.md)

## Shipped

> Scope note: each matter-detail tab is its own substantial area, not one line item. "Shipped" below means the tab exists and renders real data; deeper work (create/edit flows, rich text, drag-drop, in-tab search, OCR, deadline auto-generation, conflict checks) belongs to dedicated phases.

- [x] **Drafts and originating document** (2026-10-20, ADR-056) — `/matters/new` saves and resumes drafts (visible to the creator, the chosen lead and team seats holding `matters.create`, and Admins) (values plus intake files, one marked as the originating document; drafts untouched for 90 days are swept by the daily `/api/matter-draft-sweep` cron). Every new matter has a `MatterAgreement` (status, signed date, linked document) shown as an Overview card, editable with `matters.agreement.edit`. Admins can turn on a firm switch that requires a signed originating document to create a matter or convert a lead; the label is per practice area. Settings: [settings-admin](settings-admin.md).
- [x] **New matter: venues, name template, dates, required fields** (2026-10-20, ADR-055) — location is a firm `Venue` picked on the form (`Matter.venueId`), shown with its address in the overview's Case facts and available to templates as `matter.venueAddress` (plus its lines and city/state/zip); the name is built from the area's template, else the firm's, and stays editable with "Reset to auto". Filed and trial dates are pickers on create and edit. Required fields are set per practice area and checked server-side on create before the conflict check; on edit a filled required field can't be cleared but an empty one doesn't block the save. A required incident date only applies when the area tracks the SOL. Venue and required-field settings: [settings-admin](settings-admin.md).
- [x] **Billing types** (2026-10-21, ADR-060) — one billing type per matter (Hourly, Flat fee, Contingency, Court-appointed, Pro bono; legacy Hybrid display-only), derived from `feeStructure` + `billingMode` in `src/lib/billing-type.ts`. Each practice area lists the allowed types and a default (Settings, Practice areas); the new-matter form and lead conversion offer only those, preselect the default, and the server rejects others. Locked after creation: changing it on the edit form needs `matters.billing_type.edit` (Admins implicitly), may pick any type, and is logged. Shown in the matter header and as the list filter/sort (`?fee=`, Court-appointed filters on the voucher mode). The fee-petition billing mode is no longer selectable (existing values kept) until it gets its own switch.
- [x] **Matters list — route + table** — route, table, real data, click-through to detail.
- [x] **Matters list — sort & filter** — URL-backed state (ADR-007/009), 8 filter dimensions, sortable column headers. Search and sort apply before paging (`?page=N`, 200 per page); past the 5,000-row in-memory sort bound the page says so; pinned matters sort first; deadline windows use the viewer's calendar day.
- [x] **Matters list — Table / Kanban toggle** — segmented control, URL-backed (`?view=kanban`). Kanban shows one column per stage present in the filtered result (empty stages get no column); cards show area/billing type/lead/trust/next deadline.
- [x] **Pin toggle** — per-user pin/unpin (ADR-010); server action + revalidation; sidebar updates live.
- [x] **Overview tab** — case facts; team roster (active in brand color, former dimmed with "(former)"); preview cards for upcoming deadlines and open tasks; the full Notes section (since 2026-10-18, same composer and list as the Notes tab); Clients card with contact info. Trust/WIP facts need `billing.view` (ADR-038).
- [x] **Stage stepper — collapsed outcomes** (2026-10-18) — with 2+ terminal stages (e.g. Dismissed / Convicted / Acquitted) the stepper shows ONE end dot: "Closed" while open (hover lists outcomes), the actual outcome once reached. Change-stage menu still lists every stage; areas with one terminal stage unchanged (`stepperSteps` in `stage-changer.tsx`).
- [x] **Stage transition guard** — server returns `requiresConfirmation` for terminal -> non-terminal reopens and backward jumps > 1 stage; UI warns and retries with `force: true`. Reopens get a distinctive ActivityLog title. The Deadlines tab entry's guard is this same behaviour.
- [x] **Team management** — admin-gated section on the matter edit page (`matters.manage_team`): add/remove lead / co-counsel / paralegal / investigator / of-counsel. Promoting a lead auto-demotes the old lead to co-counsel. Removal is soft (`MatterTeamMember.removedAt`) and also detaches the member from upcoming matter events; at-least-one-lead invariant; ActivityLog on every change. Team membership is the basis of matter-team access (ADR-039, see [matter-access.md](matter-access.md)).
- [x] **Timeline tab** — chronological feed from `ActivityLog`, day-grouped (Today/Yesterday/date) with icon, source chip, author, timestamp. URL-driven filter pills (All/Filings/Communications/Deadlines/Tasks/Notes/Time/Financial/Events) with live counts; 200-row cap. Settlement and expense rows are omitted (not redacted) unless the viewer holds `matters.settlement.view` / `matters.expense.view` (ADR-021).
- [x] **Parties tab** — five fixed categories (Clients / Opposing / Lay witnesses / Expert witnesses / Others) with inline add/edit/remove and an attorney picker; names link to `/contacts/[id]`; controls hidden without `parties.create/.edit/.delete`. Every party is a first-class `Contact`; representing attorneys also via `MatterContact.representationContactId`. Re-adding a party already in the same category is refused, not overwritten.
- [x] **Deadlines tab** — due date, days remaining, kind, source, owner, status; overdue in warn color. Row menu: Edit, Set status (open/completed/waived), Delete. Stage-transition guard confirmation as above.
- [x] **Tasks tab** — grouped by status (Open / In progress / In review / Done / Cancelled) with priority chip, due date, owner. Inline status toggle; row menu: Edit, Log time, Add note, Convert to deadline, Set status, Delete. (Dashboard "Your tasks" offers only Log time / Add note.)
- [x] **Notes tab** — cards with type chip (Note/Strategy/Chatter/Memo), author avatar, timestamp; pinned float to top. Tiptap rich-text editor; HTML sanitized server-side via `sanitizeUserHtml` (`sanitize-html`, not DOMPurify) on insert. Delete, pin and edit are activity-logged.
- [x] **Captures and notes — per-kind permissions** (2026-10-16, ADR-025) — every record kind created through a note or primary capture needs its own create key (`tasks.create`, `events.create`, `deadlines.create`, `time_entries.create`, `notes.create`; `notes.pin` for pinned), checked before any write via `src/lib/capture-permissions.ts`. Deleting a note others replied to needs `notes.delete_any`. Sibling and Events-tab events get `createdById`, default attendees (`src/lib/calendar-default-attendees.ts`) and a Google Calendar push after commit. `NoteComposer` hides Pin without `notes.pin` (`canPin`, fails closed).
- [x] **Events tab** — calendar events linked to the matter, split Upcoming / Past with time, type chip, location, attendee count. Click opens EventDetailModal via `?event=<id>`. Events the viewer can't see render as non-expandable "Busy" shells using `canViewEventDetails` (ADR-021).
- [x] **Statute of limitations integrity (ADR-027)** — matter SOL fields are the source of truth; the SOL deadline is a ONE-WAY mirror (matter -> deadline) that refuses date moves/deletes (status changes allowed; the row edits status only; matter saves keep its status and owner). Edit form auto-recomputes an auto-derived SOL from incident date + area (live preview; override input only for real manual dates), never wipes SOL data when switching to an area without SOL tracking, and keeps the stored date if the incident date is cleared; an auto-derived SOL follows incident/area edits while a manual override is kept. Lead-attorney change on the edit form requires `matters.manage_team`; current client/lead always stay in the option lists. Create/update/satisfied and all deadline mutations write the activity log.
- [x] **Statute-of-limitations tracking** — `Matter.incidentDate`, `PracticeArea.statutePeriodAmount/Unit`, `statuteSourceCitation`. Practice-area form takes amount + unit (days/months/years). Matter create/update and lead conversion auto-populate `statuteOfLimitationsDate` with calendar arithmetic (Feb 29 + 1 year = Feb 28; month ends clamp; ADR-035; explicit SOL date wins). Mirrors into a `kind="critical"` Deadline via `syncMatterSolDeadline`, kept synced on create/update/satisfied-flip.
- [x] **Conflict gate on matter writes** (2026-10-20, ADR-054) — the edit form (a changed client or opposing party / firm) and the Parties tab (adding an opposing party with its counsel, or a co-client) run the same gate as creation below.
- [x] **New matter: conflict check and team** (2026-10-20, ADR-054) — `createMatter` screens the client against adverse parties and the opposing party / firm against the firm's clients before writing. Warn needs a "reviewed" tick, conflict an override (`intake.conflict_check.override`, justification on the matter timeline); the acknowledgement is tied to a fingerprint of the result. Extra team seats (any non-lead role) with `matters.manage_team`, written in the create transaction, logged and notified in-app. Practice-area deadline rules and task lists already apply on create (see [deadlines-and-tasks](deadlines-and-tasks.md)).
- [~] **New matter form — v1** — `/matters/new` with full intake fields, typeahead client picker (defaults to inline new Contact), auto-populated matter name with dirty-tracking and "Reset to auto". Single write of Matter + MatterTeamMember + optional UserMatterPin + optional new Contact. Page enforces its own permission gate.

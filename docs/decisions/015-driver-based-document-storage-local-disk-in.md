# ADR-015: Driver-based document storage — local disk in dev, Vercel Blob (client-direct + 302 serving) in prod

**Date:** 2026-07-07
**Status:** Accepted — the _public-access_ parts (bearer URLs, redirect to the bare blob URL) are superseded by ADR-018 (private store + presigned URLs). Driver selection, key scheme, client-direct uploads and 302 serving still stand.

**Context:** `src/lib/file-storage.ts` wrote to `./uploads/` — ephemeral on Vercel's serverless filesystem, so every uploaded document would vanish between deploys/invocations. Worse, Vercel caps serverless request bodies at ~4.5MB, so the streaming busboy upload route (`/api/documents/upload`) physically cannot receive GB-scale discovery media in production, no matter where it writes.

**Decision:**

- **`file-storage.ts` is now a facade over two drivers** (`src/lib/storage/`): `local` (unchanged semantics — dev default, what the test suite runs) and `vercel-blob` (`@vercel/blob`: `put`/`del`/`head`). Selection: explicit `STORAGE_DRIVER` env wins; otherwise the presence of `BLOB_READ_WRITE_TOKEN` selects `vercel-blob`; a bad `STORAGE_DRIVER` value or a blob driver without a token **throws** — misconfiguration must never silently write prod uploads to an ephemeral disk.
- **Key↔URL mapping:** one key scheme everywhere, `{rand16}__{sanitized-name}` (`src/lib/storage/storage-key.ts`, client-safe/isomorphic). Local: `Document.fileUrl` holds the bare key, bytes at `./uploads/{key}`. Blob: the key is the blob _pathname_; `Document.fileUrl` holds the **full blob URL** (`https://<store>.public.blob.vercel-storage.com/{key}`) — it's what `del`/`head` accept and what serving redirects to. **Writes dispatch on the active driver; reads/deletes dispatch on key shape** (`isBlobKey` = starts with `https://`), so switching drivers never strands rows written under the old one.
- **Prod uploads go client-direct** (`/api/documents/upload/blob`, `handleUpload` from `@vercel/blob/client`): browser asks for a scoped one-time token (`onBeforeGenerateToken` = session + `documents.upload` + matter/folder validation + `allowedContentTypes`/`maximumSizeInBytes` derived from the shared extension map — the same server-derived-MIME rule as the streaming route), PUTs bytes straight to Blob (multipart), then Vercel's signed callback (`onUploadCompleted`) creates the Document row + audit entry from the `tokenPayload` _we_ signed. The busboy streaming route **stays**: the completion callback can't reach localhost, so local dev keeps the local driver + streaming route (it 501s under the blob driver). The uploader component picks its transport from a `storageDriver` prop supplied by the server component via `activeStorageDriver()`.
- **Serving under the blob driver is a 302** to the blob URL from `/api/documents/[id]/download` after the same session gate + document lookup + existence probe. Vercel's CDN handles Range/seeking. Disposition forcing: `@vercel/blob` (v2.6.0) does **not** allow a custom Content-Disposition at upload — the CDN serves inline (filename from the pathname) and the only lever is the `?download=1` query param. So the route redirects inline-allowlisted types to the bare URL and everything else to the `?download=1` variant, mirroring the local path's UX.
- **Per-file activity rows on the blob path** (vs one-per-batch on the streaming route): each client upload completes via its own independent callback; there is no server-side batch to group. Likewise blob batches are not all-or-nothing — files completed before a mid-batch failure stay uploaded.

**Trade-offs (the honest part):**

- (-) **Blob URLs are unguessable-but-public bearer URLs.** `access: "public"` means anyone holding the URL can fetch the bytes — the download route gates who is _handed_ a URL, but a leaked URL grants access until the file is deleted (re-uploading generates a fresh random key, rotating the URL). We also set `cacheControlMaxAge` to 1 hour (SDK default: 1 month) because deletion does not purge already-cached CDN copies — the post-delete exposure window is bounded by that TTL. Upgrade path if this becomes unacceptable: `@vercel/blob` v2.6+ supports `access: "private"` + presigned GET URLs; the 302 branch would redirect to a short-lived presigned URL instead.
- (+) In exchange, user content is served from **blob.vercel-storage.com — an isolated origin**. Attacker-uploaded HTML/SVG rendered there has no access to our cookies/session, which makes the download route's inline-XSS allowlist moot _for that path_. The allowlist **stays** for the local driver, where bytes stream from OUR origin and inline `text/html` would be stored XSS riding a colleague's session; on the blob path the same set is reused only as a UX signal (inline preview vs forced download).
- (+) GB media uploads/downloads never transit our serverless functions (body caps, execution-time billing, memory).
- (-) `onUploadCompleted` is untestable locally (public-internet callback) and eventually-consistent: a just-uploaded file can miss the first `router.refresh()`; the uploader refreshes a second time ~2s later. Row-creation logic is unit-tested with prisma mocked (argument contract, not DB behavior).
- (-) Server-side `put` (composer form, generated templates) still rides a serverless request, so it stays small-file-only (~4.5MB platform cap) — acceptable: those paths are for typed documents, not media.
